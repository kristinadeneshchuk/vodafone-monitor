# Нотатки від №2 для №3 і №4

## Для №3 — дві речі в базі

### 1. Файл `mentions.db`, який ти скидав, старіший за `db.py`

У ньому схема без `published_at` і без `brand_query`:

```
CREATE TABLE mentions (id, source_type, source_name, text, url, text_hash, created_at)
```

А в `db.py` вже правильна, з `published_at` і `brand_query`. Просто видали старий
файл і перегенеруй: `python db.py`. Інакше №4, №5 і №6 напишуть код під схему,
якої немає.

### 2. Дедуплікація по тексту вбиває детекцію сплесків — це критично

Зараз `text_hash` рахується тільки з тексту і має `UNIQUE`. Перевірив:

```python
# три різні джерела, однаковий короткий текст "Немає інтернету"
передано: 3 | збережено: 1
```

Тобто якщо 20 людей у різних каналах напишуть «нема інтернету», в базу
потрапить **одна** згадка. Сплеску не буде, детектор №5 нічого не побачить,
і система пропустить саме ту кризу, заради якої існує.

Пропозиція: рахувати хеш від джерела + URL + тексту, а не від тексту:

```python
def generate_text_hash(m):
    key = f"{m['source_type']}|{m['source_name']}|{m.get('url','')}|{m['text'].strip().lower()}"
    return hashlib.sha256(key.encode('utf-8')).hexdigest()
```

Це прибирає повторний збір того самого поста (нам це й потрібно), але
зберігає однакові скарги від різних людей — а вони і є сигналом.

Одна новина, передрукована 10 каналами, тоді теж збережеться 10 разів. Це
нормально: для новин №5 рахує унікальні джерела окремо, а «підхопили 10 каналів»
саме й означає, що тема пішла в медіа.

### 3. Дрібниця: `url` у старій схемі був `UNIQUE`

У Telegram URL унікальний завжди, конфлікту не буде. Але якщо повернеш `UNIQUE`
на `url` — у Google News порожній `url` двічі не вставиться. Краще не повертай.

## Для №4 — що приходить з Telegram

`source_type = 'telegram'`, `source_name` = юзернейм каналу, `url` = `https://t.me/<канал>/<id>`.

Особливості цих текстів, які варто врахувати в промпті:

- **Емодзі й розмітка** трапляються часто, текст іноді починається з `🔴` або `❗️`.
- **Пости-агрегатори**: один пост може згадувати двох операторів у порівнянні
  тарифів. Такий пост я записую двічі — по разу на бренд, `text` однаковий.
  Твій аналіз має дивитись на `brand_query` і оцінювати тональність **щодо цього
  бренду**, а не загальну тональність тексту. Інакше новина «Київстар підняв
  ціни, Vodafone лишив старі» дасть негатив для обох.
- **Сарказм** — у телеграмі його більше, ніж у новинах:
  «дякую водафону за чудовий зв'язок, четвертий день без мережі» це `-1`.
- **Рекламні пости** операторів заходять у вибірку. Для них `msg_type: ad`,
  вони не повинні потрапляти в позитив і псувати тренд настроїв.
- Пости коротші за 15 символів я відкидаю ще на зборі, тож сміття на кшталт
  «підписуйтесь» до тебе не доходить.

Регекс у мене ловить відмінки через `водафон\w*`, тому в базі будуть і
«водафону», і «водафоні». Локацію нормалізуєш ти — «у Львові» має стати
`Львів`, інакше кластери розсиплються.
